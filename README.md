# Sala · ศาลา

หลังบ้านสำหรับเอเจนซี่เช่าอสังหาฯ หลายเจ้าในระบบเดียว แต่ละเจ้าเก็บทรัพย์ สัญญาเช่า
และเงินของตัวเอง โดยมองไม่เห็นข้อมูลของเจ้าอื่นเลย

ชื่อมาจาก **ศาลา** — ที่พักส่วนกลางที่ทุกคนมารวมกัน และบังเอิญว่า *sala* ในภาษาสเปน
กับอิตาลีแปลว่า "ห้อง" พอดี

ยังไม่มีโค้ด — ตอนนี้มีแต่ข้อตกลงว่าจะสร้างอะไร ดู [CONTEXT.md](./CONTEXT.md)
สำหรับคำศัพท์ที่ใช้ทั้งระบบ และ [docs/adr/](./docs/adr/) สำหรับการตัดสินใจที่กลับตัวยาก

## ที่มา

Sala โตมาจาก [the-cozy-keys](../the-cozy-keys) ซึ่งเป็นหลังบ้านของเอเจนซี่เจ้าเดียว
Cozy Keys จะย้ายเข้ามาเป็น Org แรกแล้ว repo เดิมจะถูก archive —
เหตุผลอยู่ใน [ADR 0003](./docs/adr/0003-cozy-keys-becomes-org-one.md)

## ขอบเขต v1

เข้า: ทรัพย์และอาคาร · เจ้าของ · สัญญาเช่าและผู้เช่า · ตารางชำระเงิน · เอกสารสัญญา ·
ลูกค้าที่ติดต่อเข้ามา

ไม่เข้า: หน้าเว็บสาธารณะ (ไม่มีเลย — Sala เป็นหลังบ้านล้วน) · ตัวสร้างโพสต์ด้วย AI ·
การเก็บเงินค่าใช้ระบบ

เอเจนซี่เข้าระบบด้วยคำเชิญเท่านั้น ไม่มีหน้าสมัคร ไม่มีแพ็กเกจ

## รูปร่างระบบ

```
เบราว์เซอร์
  │  อ่าน  ──────────────────────────►  Supabase (RLS กรอง org)
  │  เขียน ──►  Server Action           ▲
  │             requireMember(org) ─────┘
  │
n8n / LINE bot
     └──► POST /api/intake/inquiries ──► ตรวจโทเกนของ org ──► insert

cron 03:00 Asia/Bangkok ──► service role ──► ปิดสัญญาที่หมดอายุทุก org
```

- URL มี Org อยู่ในเส้นทาง: `/o/cozy-keys/properties` — คนหนึ่งคนอยู่ได้หลาย Org
  และสลับด้วยการเปลี่ยน URL ไม่ใช่ state ที่ซ่อนอยู่ใน cookie
- ทุกตารางมี `org_id NOT NULL` และ policy ชุดเดียวกันหมด มีเทสต์สแกน `pg_policies`
  ไม่ให้ตารางไหนหลุด — [ADR 0001](./docs/adr/0001-shared-database-with-rls.md)
- เขียนผ่าน Server Action เท่านั้น อ่านยังยิงตรงจากเบราว์เซอร์ได้ —
  [ADR 0002](./docs/adr/0002-writes-through-server-actions.md)
- ไฟล์แนบอยู่ใต้ `{org_id}/...` และ policy บน `storage.objects` เทียบโฟลเดอร์แรก
  กับ Membership ไม่มี fallback เป็น base64 — อัปโหลดล้มคือล้ม

## แผนสร้าง

Scaffold Next.js ใหม่ แล้วยก `lib/payments.ts`, `lib/validate.ts`, `types/` และเทสต์
จาก Cozy Keys มาตรงๆ เพราะเป็น TypeScript เพียวไม่ผูก framework — ตรรกะอย่าง
`buildPaymentSchedule` (ที่จัดการเคส 31 ม.ค. + 1 เดือน → 28/29 ก.พ. ไว้แล้ว)
ไม่มีเหตุให้เขียนใหม่ ส่วน `app/` สร้างใหม่ทั้งหมดเพราะทุกหน้าต้องอยู่ใต้ `/o/[slug]` อยู่ดี

กฎ "ห้ามใช้ nested select" ของ Cozy Keys ยกมาก่อน แต่มันเป็น workaround ของ policy
ชุดเก่า — เขียนเทสต์ยิง nested select ข้าม 2 Org แล้วดูว่าแถวครบไหม ถ้าครบก็ทิ้งกฎได้
